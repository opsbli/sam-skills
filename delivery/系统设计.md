## 1. 引言

### 1.1 文档目标

- **一句话定位**：本文档定义 sam-skills（发布身份 opsbli/sam-skills）在交付物中的所有系统级架构设计产物——把《高层架构设计》冻结的业务边界（本地 CLI/Skills 仓库、三层业务架构、五大模块组 M1~M5 与底座 B1~B4、MVP=N1~N3）落成研发与下游文档（部署/安全/UserStory）可直接消费的系统蓝图。
- **读者对象**：架构师 / 维护者（贡献者）/ 下游文档 Owner（platform-architect、security-architect、product-story-designer）/ 评审委员会。
- **设计范围**：业务架构 + 应用架构 + 数据库设计（文件型数据设计）+ 部署架构（本地运行与分发）+ 安全设计（合规底线）+ 可观测设计；网络架构未启用（见 §0 裁剪声明）。
- **明确不做**：本文档不重写业务价值与产品目标（归 business-architect）；不输出资源预算与发布流水线（归 platform-architect 的《部署设计》）；不输出完整威胁模型与安全方案（归 security-architect 的《安全设计》）。

**关系模式说明**（本项目适用性注记）：

| 关系模式 | 适用场景 |
| --- | --- |
| Customer/Supplier | 上下游强协作，下游能影响上游节奏：harvest 提案→技能修订，批准节奏由维护者控制 |
| Conformist | 顺从者，下游完全遵循上游模型：fork 对上游基线 6654f6b 的 overlay 继承 |
| ACL（Anticorruption Layer） | 对接外部强势平台必用：三家宿主 harness 各建真适配器，能力表单点维护 |
| Shared Kernel | 共享内核，维护成本高慎用：仅限 CONTEXT.md 五术语这一小块纯 glossary |
| Published Language | 标准协议多下游消费：receipt v2 契约（Schema 首字段锁定，多消费方） |

#### 2.2.3 跨域协作原则

| 原则编号 | 原则 |
| --- | --- |
| P-01 | 核心域 → 支撑域/通用域禁止反向依赖：契约执行上下文不感知评审上下文内部结构（spec-executor 只消费 SPEC READY 与产出 receipt，评审是执行线程内的模型触发行为） |
| P-02 | 核心域之间禁止直接耦合，必须通过契约工件解耦：规划访谈→契约执行之间只传 SPEC READY 启动块（不传 grill 历史——D76，§能力对照表「继承保持契约级」）；契约执行→证据回灌之间只传 receipt v2 |
| P-03 | 对接外部不可控系统必须建 ACL 防腐层：宿主 harness 能力面（fork_thread / spawn_execution 等）只允许存在于各自适配器文档（capability map / MCP 服务）单点，禁止贯穿到技能语义层（ADR 0003） |
| P-04 | 跨上下文崩溃恢复以持久化工件为准：SPEC READY 块、执行锁、receipt 三工件任何一方崩溃后可重建会话状态（D27，§守卫），禁止依赖会话内存状态跨上下文传递 |
| P-05 | 修订必须经人工批准回路：任何对技能资产（SKILL.md / 规范文档）的修改只能经 draft proposal 显式 Approved: yes（D30），台账 append-only 不回写 |

#### 2.5.2 业务柔性可用策略

##### §3.2.M1.3 关键结构定义

**SPEC READY 启动块（O-01）结构骨架**（8 字段，D42；启动块是已批 spec 的索引不是替代品）：

```text
SPEC READY
- Status:            ready | not-ready
- Source:            spec issue / tracker 引用
- Repository:        仓库路径与分支
- Baseline:          固定点（SHA / 分支 / tag）
- Test seam:         约定的测试接缝清单（默认一 spec 一 seam）
- Non-goals:         明确不做项
- External authority: 外部权限信封（默认不授 commit/push/deploy）
- Next route:        fork | to-tickets | express lane
（not-ready 时改发 SPEC NOT READY 并列出缺失项，不启动实现）
```

**关键字段定义表**：

| 字段 | 类型 | 必填 | 业务含义 | 约束 / 默认值 |
| --- | --- | --- | --- | --- |
| Status | 枚举 | 是 | 成稿状态 | ready / not-ready；not-ready 禁止进入执行 |
| Source | 引用 | 是 | spec 正文出处 | 指向 tracker issue，不重复全文 |
| Baseline | 引用 | 是 | 执行基线固定点 | SHA/分支/tag；执行锁继承此值（M2） |
| Test seam | 清单 | 是 | 红绿循环的接缝约定 | 优先既有 seam，新 seam 与用户核对 |
| External authority | 枚举 | 是 | 外部权限信封 | 默认 none：不授 commit/push/deploy 等外部权限（D27） |
| Next route | 枚举 | 是 | 执行路由 | fork / to-tickets / express lane（§3.2.M2 判定） |

**Goal 工件（O-04）结构骨架**（D41，六节）：

```text
- Goal:                一句话目标
- Current state:       起点状态
- Execution order:     执行顺序
- Completion criteria: 机器可查复选框（一条件一复选框，禁复合条件）
- Constraints:         约束清单
- Context:             上下文（含条件注释块）
```

#### 3.5.2 幂等性约定

本地形态下「重复执行有副作用」的写入操作分类与幂等机制：

| 写入类型 | 是否要求幂等 | 幂等机制（等价于模板幂等键） |
| --- | --- | --- |
| 信箱投递（MCP spawn_execution） | **强制幂等（exactly-once）** | 投后即置 delivered（D69）；重复投递被状态机拒绝 |
| 执行锁获取 | 强制幂等（互斥） | 原子 mkdir：重复获取失败（201002）；释放仅在 done/fail/release |
| 台账追加（DF-02~DF-04、DF-06） | 强制幂等（防重复行） | 一事一行 + 关联标识（receipt 标识/任务名/日期）；追加前按关联标识查重；append-only 单向 |
| draft proposal 创建 | 强制幂等 | 一缺陷一文件 + 命名规则（日期-技能名-短标识）；同名存在即跳过并提示 |
| harvest apply 应用 | 强制幂等（防重放） | old text 原位核对：已应用则 old 不在原位 → 302001 停止，天然防重复应用 |
| 版本双写（sync-plugin-version） | 是 | package.json 为单源，重跑收敛到同一值 |
| 生成物重建（build-codex-plugin） | 是 | 生成物从唯一事实源（plugin.json）可确定性重建；--check 校验漂移 |
| spec/goal/工单创建 | 是 | tracker 原生唯一性 / 一票一文件命名唯一 |
| 查询类（check_mailbox、list-skills、校验只读模式） | 天然幂等 | — |

**幂等设计五问（各模块已回答）**：幂等键生命周期=工件关联标识随台账永久保留（append-only）；重复请求语义=拒绝或跳过并提示（不返回假成功）；执行中态=锁互斥（第二个获取者收 201002）；失败后可重试性=失败释放锁后可重新发起（工件重建原则，QS-05）；存储兜底=文件系统即最终事实（无缓存层，§0 裁剪声明）。

#### 3.5.3 并发与资源预算约定（限流约定的本地形态）

无网关限流；本节以「资源预算」承担同等职能（防止单点过载与失控消耗）。5 维预算：

| 维度 | 默认值 | 触发动作 | 调整方式 |
| --- | --- | --- | --- |
| 全局并发（执行线程） | 单一活跃执行线程/checkout | 第二个执行请求被拒（201002） | fork-loop-mcp 锁机制；超过 6h 陈旧锁人工破 |
| 单任务续跑预算 | Stop 续跑 ≤ 3 次（一 receipt 恰耗 1） | 预算耗尽停止续跑 | D76 固定值，改动属 ADR 级 |
| 上下文预算（规划线程） | smart zone 约 150k token；L2 正文 ≤5k token/技能 | 接近阈值仅在阶段边界 /compact | ask-matt 阶段边界五选项；D22 |
| 评审并发预算 | roundtable 全桌 2N 子代理（quick=N）；code-review 每轴 1 子代理 | 席位数 3~5 封顶；报告 ≤300/400 词 | D37/D23 固定护栏 |
| 运营频次预算 | eval 至多每周一次（技能变更后必跑）；sync drill 每次同步前一次 | 超频次不自动执行 | D14 cadence；D8 |

**降级策略**（对齐 §2.5.2 降级清单）：预算触发不静默丢弃——执行并发被拒给出明确错误码与等待指引；续跑耗尽后状态留在工件可重建；评审超限按固定护栏收敛输出。红线联动：本表数值与 §5.5 容量水位线、§8.4 告警阈值一致。

#### 3.5.4 默认超时与重试基线

全局单一来源；各模块接口清单（§3.2.M{N}.2）通过引用本节继承默认值，特殊场景覆盖须显式说明：

## 4. 数据库设计（文件型数据设计）

> **本章回答**：每个模块的状态用什么文件存、列结构怎么定义、数据怎么清理、版本怎么管。
> **形态映射声明**（§0 裁剪声明的落地）：本系统无数据库引擎。数据存储的现实形态是 repo 内文件，按以下等价映射组织，全文口径一致：**表 ≈ 数据文件/台账；行 ≈ 行记录；字段 ≈ 列结构；索引 ≈ 命名与检索约定；DDL ≈ 文件结构定义；备份 ≈ git 版本管理**。业务域与 §2.1/§3.2 保持一致（按域分组，禁止按技术维度横向组织）。

### 4.1 全局数据约定

写在所有数据文件设计之前的项目级数据基线：

| 约定项 | 取值 | 说明 |
| --- | --- | --- |
| 命名规范（数据文件） | 台账类：docs/〈语义名〉.md（kebab-case）；提案类：日期-技能名-短标识.md；工件类：随会话/跟踪器命名约定 | 全仓统一 kebab-case，与 §3.5.5 命名风格一致 |

| 时间字段 | 日期用 ISO 8601 短横线格式（例如 2026-09-11，台账行首列）；时间戳用 ISO 8601 完整格式（机器报告行） | 与台账人类阅读习惯及机器解析双轨对齐 |

| 审计字段 | 每台账行含日期列；机器报告行含 timestamp；修订类文件含 Applied: 行 | 谁（会话/维护者）何时对什么工件做了什么，经 git 提交记录补全 |

| 状态枚举 | Markdown 行内枚举（人类可读全列）+ 机器报告行 JSON 枚举 | 枚举取值在字段定义表全部列出（如 Conclusion：completed/blocked/failed） |

| 敏感字段 | 秘密不入台账：凭据留环境变量，产出前先脱密（D25/D39）；台账与 receipt 只记事实不记值 | 与 §7.2.2 数据安全联动 |

#### 4.3.1 存储清单（本地形态）

#### 4.3.2 备份与恢复

| 维度 | 取值 |

| 保留策略 | git 历史永久保留；远端仓库由 GitHub 平台冗余；release/tag 长期保留 |
| RPO（数据丢失容忍） | 已提交数据 RPO = 0（git 提交即持久）；未 push 的本地提交 RPO ≤ 24h（维护节奏：台账变更当日入库，配合每周 eval / 每季 drill 的既有节奏，MVP 期建议台账变更即 push） |
| RTO（恢复时间目标） | ≤ 30 分钟（本机故障场景：git clone 远端仓库 + 恢复本机环境：Node 18 安装与宿主插件重装；恢复步骤 ≤ 6 步） |
| 恢复演练 | 频率：随每次上游同步 drill 顺带核验（clone 远端到临时目录跑 lint 门禁链，零额外成本）；负责人：仓库维护者（opsbli） |

**自洽性说明**：本地工具无对外 SLA（§5.3），RPO/RTO 是维护者侧的数据安全承诺而非用户合同承诺；与 §5.2 韧性口径一致（工件可重建 > 备份恢复）。
