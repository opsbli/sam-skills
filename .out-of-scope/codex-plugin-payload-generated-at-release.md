# Generating the Codex plugin payload at release instead of committing it

`.codex-plugin/` is a committed, generated mirror of the promoted skills: 32 skill directories plus `plugin.json` and `hooks/hooks.json`, regenerated by `node scripts/build-codex-plugin.mjs`. Keeping it out of git — building it in the release workflow, vendoring it as a submodule, or replacing it with a symlink — is out of scope.

## Why this is out of scope

Three reasons, none of which depends on when the question gets asked.

**The constraint is a manifest limitation, not a preference.** A Codex manifest accepts exactly one skills path and discovers skills recursively under it (ADR 0002). The payload therefore has to exist as a real directory tree with real `SKILL.md` files at the moment the plugin is read — nothing can synthesise it on demand. A symlink does not survive the trip either: this repo is developed on Windows, where `core.symlinks=false` materialises a symlink as a small text file containing its target path, which is a directory of nothing so far as a manifest reader is concerned.

**The git repository is a documented install source.** Both supported Codex install routes — `codex plugin marketplace add opsbli/sam-skills` and `npx skills@latest add opsbli/sam-skills` — read the published repository directly. A payload that exists only as a release artifact would make the repository un-installable and require a second, separately documented distribution channel plus a second install story to support and keep honest. Paying that cost to remove a build artifact from git is a bad trade.

**The drift cost is already bounded and detectable.** The mirror can only go stale in the window between editing a skill and regenerating; `build-codex-plugin.mjs --check` closes that window mechanically and runs in CI and in the pre-push hook, comparing every file byte-for-byte (line endings normalised, since CRLF is a checkout artifact rather than drift). What this direction would buy is a smaller `git diff`; what it would cost is an install path that no longer works from the repository everyone already has.

**One accepted cost, stated plainly.** The generator is not allowed to be a partial description of the payload. It was, briefly: it emitted skills and `plugin.json` but not the `mcpServers` block or the Stop hook, so `--check` was permanently red and running the generator would have silently stripped the Codex plugin's automatic transport while turning the check green. That was fixed in the generator, not by relaxing the check — the rule being: every hand-added part of the committed payload needs a counterpart in `build-codex-plugin.mjs`, or `--check` is measuring the wrong thing.
